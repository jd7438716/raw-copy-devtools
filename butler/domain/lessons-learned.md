# 经验教训 — Butler 系统开发

本文件记录 Butler 开发过程中值得记录的经验教训，供后续维护者参考。

---

## LL-001：LLM 软约束 vs 文件系统硬信号

**场景**：Captain 需要在 evidence 不全时被阻止 claim [goal:complete]。

**第一次尝试**：修改 Captain prompt，添加 "如果证据不全则 [goal:blocked]" 指令。

**问题**：LLM 存在幻觉风险，prompt 指令可能被忽略或 "忘记"。在高复杂度任务中，LLM 更容易专注于代码实现而忽略验收规则。

**最终方案**：plugin 写 `.blocked-{slug}` 硬信号文件，Captain prompt 在 claim 完成前必须读取该文件。这是确定性的——不依赖 LLM "记住" 某个指令。

**教训**：
- 关键的质量门禁不应仅依赖 prompt 指令（LLM 软约束）
- 文件系统信号是确定性的代理（agent 执行流程的硬编码步骤）
- 规则：如果某个失败模式的后果严重（P0/P1），必须有硬编码的兜底机制

**适用场景**：任何 "必须阻止" 的场景（安全门、质量门、审批门）。

## LL-002：Event Loop 阻塞的隐性代价

**场景**：审批轮询使用 1s 间隔轮询 120s。

**忽视点**：原以为 "只是等一下"，实际上阻塞了整个 event loop 120s。这 120s 内所有 heartbeat、session.idle 事件全部堆积。

**修复**：替换为 fs.watch 事件驱动。

**教训**：
- 在单线程事件循环架构中，任何同步等待都是"全局暂停"
- 评估改动时不仅要看 "这个操作本身多快"，还要看 "它阻塞时其他操作怎么办"
- 规则：超过 100ms 的同步操作必须质疑其合理性

## LL-003：原子写入的启动清理

**场景**：`writeJob()` 使用 `.tmp` + `renameSync` 原子写入。

**忽视点**：原以为原子写入就够了，但进程在 `writeFileSync` 和 `renameSync` 之间崩溃会残留 `.tmp` 文件。

**修复**：启动时 `cleanupStaleTmpFiles()` 清理超 1h 的 `.tmp` 文件。

**教训**：
- 原子写入的标准最佳实践应包含"启动时清理"和"写入时校验"
- 文件系统的"不变量"不只包含正常路径，还包含所有崩溃恢复路径

---

## LL-004：指数退避的代价平衡

**场景**：session.get 失败后的重试策略。

**选择**：固定间隔（2s, 5s）vs 指数退避（2s, 4s, 8s + jitter）。

**教训**：
- 固定间隔适合"恢复时间可预测"的场景（如本地服务重启）
- 指数退避适合"恢复时间不确定"的场景（如网络切换、远端服务恢复）
- jitter（随机抖动）防止多个 client 同时重试造成 "惊群效应"

## LL-005：静态黑名单 vs 动态语义

**场景**：防止 "决定不做 XX" 被误采集为 knowledge。

**第一次尝试**：精确匹配 "不做"、"取消" 等关键词。

**问题**：语言变体太多（"暂缓"、"延后"、"不予采纳"、"否决" 等）。

**最终方案**：18 个否定模式的正则黑名单。

**教训**：
- 语言过滤本质上是 NP-hard 问题，没有完美的静态方案
- 好的工程实践是"覆盖 95% 的常见变体 + 接受少量误报"
- 与其追求完美的 NLP 方案，不如用简单的黑名单 + 定期人工审核

## LL-006：最小侵入原则

**场景**：21 项修复需要在多个文件中做改动。

**策略**：每项修复尽量不改变原有代码结构，只在外层添加保护或在内层添加最小改动。

**好处**：
- 容易 review（diff 集中在新增逻辑）
- 容易回滚（删除新增代码即可）
- 不破坏原有代码的可读性

**教训**：当修复范围涵盖整个系统时，"最小侵入"比"完美重构"更重要。先修复再优化。

---

## LL-007：文件系统作为通信总线的双面性

**场景**：Butler 系统通过 butler/ 目录下文件交换信息。

**优势**：零外部依赖、天然持久化、人工可读可调试。

**代价**：
- 没有原子性保证（需要手动 .tmp + rename）
- 没有通知机制（需要 fs.watch 或轮询）
- 没有 schema 校验（需要手动验证字段）

**教训**：选择文件系统作为通信总线是因为简单和透明，但必须为它的局限性做好准备：原子写入、启动清理、字段校验是标配。

## LL-008：分析卡点的系统方法论

**场景**：如何全面地找出系统中的所有卡点？

**方法**：混合使用多种系统工程学方法论：
- VSM 找延迟
- Little's Law 量化瓶颈
- TOC 聚焦核心约束
- 控制论判定闭环完整性
- FMEA 穷举错漏

**教训**：单一视角只能看到部分问题。用多种方法论交叉验证，才能获得完整的系统图景。

## LL-009：通用工具不应预设领域

**场景**：为 Butler 研究员创建搜索策略配置。

**第一次尝试**：创建 `researcher-config.yaml` 硬编码 travel/education/health 分类。

**问题**：Butler 是通用 AI 应用开发工具，预设特定领域分类与通用定位矛盾。真实场景的法律/金融/医疗等领域无法穷举。

**最终方案**：删除配置文件，改为 LLM 从项目 overview.md 动态推断领域和搜索策略。

**教训**：
- 通用工具的配置应该是"动态推断"而非"静态枚举"
- 规则：如果某个分类列表需要不断新增项，说明应该用动态推断替代
- 先分析项目才知道领域，不能预先写死

**适用场景**：任何"通用平台 + 领域配置"的设计决策。

## LL-010：新增 Agent 必须验证全链路

**场景**：创建了 butler-app-researcher、butler-researcher-generator、butler-skill-discovery 三个新 agent。

**忽视点**：只写了 agent 定义文件，未验证谁调用它、谁消费它的输出。

**问题**：审计发现 4 条链路断裂：
1. butler-init 不调用 researcher-generator → 生成器永远不被触发
2. research-context.md 写入后 strategist 不读 → 研究成果浪费
3. skill-discovery 未在 coordinator 注册 → 无法被调度
4. updateResearchStatus 是 TS 函数 agent 调用不到 → 状态报告断路

**教训**：
- 新增 agent 必须绘制完整链路：触发者 → agent → 输出 → 消费者
- 规则：每个 agent 定义文件写完后，必须回答 3 个问题：
  1. 谁调用我？（触发条件）
  2. 我输出到哪里？（文件/API）
  3. 谁消费我的输出？（下游 agent）
- 如果任一答案为空 → 链路未闭合，需要修复

**适用场景**：任何新增 agent/skill/plugin 时。

## LL-011：Agent 与 Plugin 的通信只能通过文件

**场景**：设计研究进度追踪机制。

**第一次尝试**：在 butler-analysis.ts 中写 `updateResearchStatus()` TS 函数，让 agent 调用。

**问题**：Agent 是 prompt 文本，无法调用 TypeScript 函数。Agent 只能通过写文件与 plugin 通信。

**最终方案**：Agent 写 `.research-status-{slug}` JSON 文件 → plugin 读取文件 → 展示。

**教训**：
- Agent ↔ Plugin 通信的唯一可靠方式是文件系统
- 不要设计"agent 调用 plugin API"的架构
- 规则：如果 agent 需要报告状态 → 写文件；如果 plugin 需要通知 agent → 写文件让 agent Step 0 读取

**适用场景**：任何需要 agent ↔ plugin 数据交换的场景。

## LL-012：验证分层防止过度阻断

**场景**：AI Agent 输出验证中，把所有必填字段一视同仁——缺了就阻断。

**问题**：LLM 的输出天然不可预测，刚性验证导致大量误阻断。用户反馈 "每跑必挂，走手动 fallback"。

**最终方案**：P0(阻断)/P1(宽容)两层验证体系。P0 字段缺失阻断，P1 字段缺失自动补默认值+WARN 继续。

**教训**：
- AI Agent 的输出验证需要区分"根本不能缺"和"缺了也能凑合用"的字段
- P0/P1 分界的决策标准："缺了这个字段管线是否还能继续运行？"
- 默认值策略保证数据结构的完整性：string→""、number→0、array→[]
- 与云原生 QoS 分层的思路一致：Guaranteed(阻断性) vs Burstable(宽容性)

**适用场景**：任何对 LLM 输出做字段级别验证的场景。

## LL-013：精确重试优于全量重跑

**场景**：质检发现问题后回到 Step 1 全量重新生成。

**代价**：每次重试浪费已成功的步骤（如文案通过了但图片失效，仍然重跑文案）。

**最终方案**：分析 issues 描述定位失败源头，只重试失败的 step。定位失败时回退到全量重跑。

**教训**：
- "发现问题→回到原点"是简单的实现，但成本很高
- 精确重试需要"问题可归因"——质检 issues 必须标注出问题属于哪个 step
- 如果归因失败，全量重跑作为安全的 fallback
- 规则：先精确再全量，精确失败时不要丢信息

**适用场景**：多 step 管线中某个 step 失败的重试策略。

## LL-014：修改生成源而非生成结果

**场景**：用户反馈 AI 应用（生成的产物）有 3 个问题——Designer 验证太严、Copywriter 不被调用、BrandOfficer 格式不兼容。

**第一次尝试**：直接修改生成的 Agent 文件（`agents_butler/{app}/agents/*.md`）。

**问题**：
- 修改结果只对一个应用有效，下次生成的新应用仍会出同样的问题
- 生成的产物不应被手动修改（会被重新生成覆盖）

**最终方案**：修改生成源 `workflow-format-spec.md`（输出格式定义）和 `butler-app-runner.md`（运行时管线）。以后再生成所有 AI 应用自动受益。

**教训**：
- 生成工具的 bug 应该修在生成器里，不是生成结果里
- 判断标准：如果问题会重复出现（每次生成都有），根源一定在生成源
- 规则：生成结果的问题 × 1 = 改结果；生成结果的问题 × ∞ = 改生成源

**适用场景**：任何模板/生成器模式的系统（如 AI 应用生成、代码生成、文档生成）。

## LL-015：计划基线必须追踪最新 commit

**场景**：写 PIPELINE-FIX-v2.md 时基线设为 `35c45c8`。但 `a8a47b9` 在当天晚些时候发布，覆盖了部分分析假设。

**问题**：审核时发现部分假设已过时（如butler-analysis.ts 又 +75 行），需要重新验证。

**最终方案**：更新基线到 `a8a47b9`，重新验证 6 项改动无冲突。

**教训**：
- 在活跃开发的项目中，计划文档的基线可能几分钟就过时
- 每次执行前必须确认基线是否仍然是 HEAD
- git 的 `--diff` 和 `--log` 是快速验证工具——执行前花 1 分钟检查总是值得的

**适用场景**：任何在活跃开发项目中协作时的计划文档维护。
