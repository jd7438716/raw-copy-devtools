# 决策链 — Git 初始化与首次提交

## 决策 1: 首个提交采用 `git add -A` 而非逐路径暂存

- **触发点**：Step 5 暂存阶段。
- **备选方案**：

  | 方案 | 优点 | 缺点 |
  |------|------|------|
  | A `git add -A` | 一步到位，不会漏文件；首次提交无历史无歧义 | 依赖 `.gitignore` 正确，否则会夹带 |
  | B 逐路径 `git add -- <files>` | 显式可控，防止误带 | 353 个文件需枚举，冗长且易漏，尤其新目录 |

- **选择**：方案 A。
- **理由**：① 项目为全新仓库、无既有暂存内容，"遗漏"风险远大于"夹带"风险，`-A` 从机制上消除遗漏；
  ② 夹带风险已由 Step 5.5 的 `git diff --cached` + `git status --ignored` 全量核对与密钥扫描覆盖；
  ③ 用户明确指示使用 `git add -A`。
- **后果**：正面 = 暂存集完整、与工作区一致；负面 = 若 `.gitignore` 有误会一并提交垃圾文件（已通过逐条 `check-ignore` 验证规避）。
- **关联决策**：引发决策 2（必须补一个正确的根 `.gitignore`）。

## 决策 2: 根 `.gitignore` 覆盖范围与对 `.refs/` 的处理

- **触发点**：Step 1 审查变更时发现无根 `.gitignore`，且 `.refs/.gitignore` 会使自身可被跟踪。
- **备选方案**：

  | 方案 | 优点 | 缺点 |
  |------|------|------|
  | A 新增根 `.gitignore` 并加入 `.refs/` | 集中管理、确保 `.refs` 不入库、语义清晰 | 根与子目录两处忽略规则并存 |
  | B 修改 `.refs/.gitignore` 追加自忽略 | 就近管理 | 改动他人约定文件，违背「不破坏既有忽略」要求 |
  | C 依赖 `git add` 时手动排除 `.refs` | 零文件改动 | 脆弱、不可复现，未来操作会重新带入 |

- **选择**：方案 A。
- **理由**：① 用户要求"必要时补一个根 `.gitignore`"，并明确"`.refs` 不应被提交"；
  ② 用户同时要求不破坏既有 `butler/.gitignore`/`.refs/.gitignore`，方案 B 违反；
  ③ 根级 `.refs/` 忽略可复现且不触碰既有文件。
- **后果**：正面 = `.refs/.gitignore` 被正确忽略（经 `git check-ignore` 验证）、外部 junction 永不入库；
  负面 = 仓库根 `butler/refs.md` 与 `butler/tools/refs.mjs` 是与 `.refs/` 无关的正常文件，会被 `grep refs` 误观（已人工确认两者应入库）。
- **关联决策**：无。

## 决策 3: 是否忽略 `butler/spec/**/e2e-artifacts` 大体积证据产物

- **触发点**：审查大文件时发现 E2E 截图/JSON 使仓库达约 8MB。
- **备选方案**：

  | 方案 | 优点 | 缺点 |
  |------|------|------|
  | A 保留并入库 | 保留验收证据，符合 Butler 知识/文档不忽略的约定 | 仓库偏大，含二进制 |
  | B 加入 `.gitignore` 排除 | 仓库更精简 | 与用户指定忽略范围不符，丢失验收证据 |

- **选择**：方案 A。
- **理由**：① 用户列出的忽略目标仅为 `node_modules`、OS 垃圾、`dist/_unzip|_verify`、`.refs`，未包含 `butler/spec`；
  ② Butler 约定明确"知识/文档类不忽略"，证据产物属验收集；
  ③ 用户指令要求"报告任何需要用户注意的文件（如大文件）"，说明预期是上报而非擅自排除。
- **后果**：正面 = 证据链完整；负面 = 首个提交体积约 9MB（已在上报中标注）。
- **关联决策**：无。

## 决策 4: 是否将 Butler 决策记录纳入首个提交

- **触发点**：Butler Git 协议要求编写 `butler/gits/{logid}/` 下的 summary/detail/decision-chain。
- **备选方案**：

  | 方案 | 优点 | 缺点 |
  |------|------|------|
  | A 纳入首个提交 | 决策记录与项目基线同时入库，结构完整 | 文件数由 353 增至 356 |
  | B 提交后再单独留作未跟踪 | 首个提交严格等于项目文件 | 留下未跟踪文件，状态不干净 |

- **选择**：方案 A。
- **理由**：① `butler/` 其余知识/流水线文档本就在首个提交内，`butler/gits` 纳入保持一致；
  ② 避免提交后 `git status` 出现未跟踪文件，保证"干净工作区"验收项；
  ③ 用户要求的是"只做 git 初始化与提交，不改业务代码/测试"——新增 Butler 文档不违反。
- **后果**：正面 = 工作区彻底干净、决策可追溯；负面 = 与用户口头预期的 353 有 3 个文件的出入（已在上报中说明）。
- **关联决策**：无。
